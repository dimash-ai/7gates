# Summary

Implement the `focal-calendar-events` backend slice (Phase 2, step 1 — non-recurring calendar-event CRUD)
on the existing scaffold. It **reuses** the shipped `app/domain/{priority,completion,daterange}.py`, the
`projects`/`activities` models, the error envelope + `get_current_user_id`, and the `tasks` router→service→
async-repo + partial-merge (`exclude_unset`) + opaque-`:id` + owned-link patterns. Four independently-green
slices: **(1) model + additive migration + schemas + the event priority helper**; **(2) create / get /
delete** (event-specific activity-aware priority resolver, enrichment, owned-link, completion-on-create,
time normalization, validation); **(3) list + PATCH** (date-window + ordering; partial-merge, null handling,
effective `endTime`, recompute, completion transition, timezone); **(4) contract test for the enriched
shape**. Every endpoint is tenant-scoped to the JWT `sub`, treats `:id` as an opaque string, and raises only
typed `AppError`. Task: [focal-calendar-events.md](../tasks/focal-calendar-events.md). Binding contract:
legacy `focal/server/{routes,storage}.ts` + `focal/shared/schema.ts` + `contract-freeze/`.

## Decisions (design + the Gate-1 contract rulings)

- **New `focal.calendar_events` table via an ADDITIVE autogenerated migration (NOT hand-authored).** No event
  model exists yet (the foundation baseline created the Phase-0/1 tables only). Add
  `app/models/calendar.py::CalendarEvent` (non-recurring column set only — see Files), then generate the
  migration with the sanctioned `uv run alembic revision --autogenerate -m "calendar events"`, **review** it
  (focal schema, indexes, nullability; ORM-side Python column defaults, not PG `server_default`), and commit
  it in-slice so `make verify` (`create_all`) + `alembic upgrade head` + `alembic check` all run against it.
  Unlike the MindMap PK swap, this is a plain `create_table` — autogenerate handles it, no exception needed.
- **Event priority = a distinct, simpler cascade (NOT the task formula).** `priority_level =
  activity.priority ?? product.priority ?? project.priority ?? "medium"` (each normalized — only
  `high`/`medium`/`low` count, else fall through); `priority_score = priority_to_score(level)`
  (`high`→1.0, `low`→0.0, else 0.5); `priority == priority_level`. **No** mission/urgency/energy term and no
  sphere `max` (legacy `computeEventPriorityFromHierarchy`, `storage.ts:126`-138, comment `:122`-125). Add a
  small `event_priority_from_hierarchy(activity, product, project)` to `app/domain/priority.py` reusing the
  existing `priority_to_score`; **do not** call the task `priority_score`.
- **Event-specific, activity-aware hierarchy resolver (the Gate-1 load-bearing ruling).** The shipped
  `tasks._hierarchy_context` **defers the activity** (`tasks.py:193`-194 — its activity term is inert), so it
  **cannot** be reused for events. The event service implements its own resolver (legacy
  `getHierarchyContext`, `storage.ts:3418`-3438): load the owned `activity`; `resolved_project_id =
  project_id ?? activity.project_id`, `resolved_product_id = product_id ?? activity.product_id`; a resolved
  product whose row carries a `parent_project_id` resolves the project when none was given; load the owned
  project/product; feed `activity`/`product`/`project` into the cascade. So an **activity-only** event still
  derives its **priority** from the activity. **Reuse only** the owned-link validation
  (`_require_owned_link`/`_owned_project`/`_owned_activity`) and `priority_to_score` — **do not modify
  `tasks`** (the existing task tests must still pass; if a helper is extracted to share, that is subordinate
  to "no task behavior change").
- **Priority is computed on create and recomputed on EVERY update** from the merged hierarchy (`merged =
  {...current, ...patch}`, `storage.ts:3935`-3941), idempotent when links didn't change. A client-supplied
  `priority` is ignored.
- **Enriched read pins the legacy `buildEnrichedEventsFromRows` shape (`storage.ts:3316`-3414), with two
  documented deviations.** Resolution uses the **stored `project_id`/`product_id` only** — *not* `activity_id`
  (that fallback is priority-context only, `storage.ts:3323`-3327): if `project_id` points to a *product*
  (a project row with `parent_project_id`), resolve `product_id = that id`, `project_id = its parent`
  (`:3346`-3350). **Resolution is via owned-project lookups (scoped to `sub`)** so a link pointing at another
  tenant's project never leaks. Emit the legacy names: `project` (project name), `product` (product name), `projectColor`
  (`product.color ?? project.color`), `projectType`, `sphere`, `isWorkTime` (default `true` w/ no project),
  `projectHasProducts`, `isOrphan` + `orphanReason` (`"noProject"` / `"noProduct"`), plus `userId`,
  `updatedAt`. **Deviation 1:** also emit `completedAt` + `createdAt` (legacy event read omits them — exposed
  for parity with `EnrichedTaskRead` + to make the completion transition observable). **Deviation 2:** omit
  the deferred columns the legacy still emits (recurrence, `sourceType`/`sourceId`/`crmInteractionId`,
  `googleEventId`/`lastSyncedAt`, `occurrenceDate`/`isRecurringInstance`). Reuse the `tasks` enrichment logic
  (stored-id resolution + orphan rules are identical).
- **Time normalization.** Accept `HH:MM` with an optional single-digit hour (legacy
  `VALID_TIME_RE=/^([01]?\d|2[0-3]):[0-5]\d$/`, `userDateTime.ts:3`); **normalize `start_time`/`end_time` to
  zero-padded `HH:MM` on store** (`9:05`→`09:05`) on **create and PATCH**, so the `(date, start_time)`
  lexical ordering is chronological (a documented hardening — the legacy stored the raw string and sorted
  lexically). `endTime` must be **strictly greater** than `startTime` (compare parsed minutes; PATCH uses
  effective values). `date` must be a real **calendar** date (format + round-trip; `2026-02-31` rejected,
  legacy `isValidDate`).
- **Null handling.** *Create:* an explicit `null`/omission for a defaulted field coalesces to its default
  (`status`→`"planned"`, `completed`→`false`, `tags`→`[]`, `contactIds`→`[]`, legacy `?? default`); required
  `title`/`date`/`startTime` have no default (null/missing → `validation_error`). *PATCH:* a `null` on a NOT
  NULL field (`title`,`date`,`startTime`,`status`,`completed`,`tags`,`contactIds`) → `validation_error` via
  `model_validator(mode="before")` (the tasks pattern); a `null` on a nullable field clears it; an omitted
  field is preserved (`model_fields_set`/`exclude_unset`).
- **Owned-link → `related_record_not_found` (400).** A supplied `project_id`/`product_id`/`activity_id`
  missing or not owned by `sub` → `RelatedRecordNotFoundError` (reuse `tasks._require_owned_link`), replacing
  the legacy raw `23503` handling. **FK + `ON DELETE SET NULL`** on all three links — matching the shipped
  `tasks` model (`tasks.py:31`-39) and the legacy schema: a deleted linked record is **auto-nulled**, so the
  event then reads as orphaned via the null id (`isOrphan`/`"noProject"` once `project_id` is null). The
  enrichment keys off the stored `project_id`/`product_id`, never `activity_id`. Ownership is **also**
  validated at the service layer (the owned-link check above) for the 400 on a bad create/patch link.
- **Completion transition** (reuse `transition_completed_at`): create with `completed=true` sets
  `completedAt`; PATCH false→true sets it, true→false clears it, omitted leaves it.
- **List** (`storage.getAllEventsEnriched`, `storage.ts:3701`): the user's events, filtered to a date window
  (`startDate`/`endDate` `YYYY-MM-DD`; **omitted or malformed → current-month default** via `get_date_range`
  — list-query dates never 422, unlike the body `date`), ordered **`date` ASC, then `start_time` ASC**
  (chronological via the zero-padding). No recurrence expansion.
- **`status` is free-form** (legacy `varchar(20)`, no enum) — any non-null string ≤ 20 chars (default
  `"planned"`); over-length → `validation_error` (column cap). `color` ≤ 20 likewise schema-validated.
- **Tenant-scoped to `sub`** on every endpoint; client `userId` (body/query) ignored; unknown fields ignored
  (`extra="ignore"`). **Fixes the legacy `GET /api/events/:id`** security bug (no ownership check,
  `storage.ts:3778`): `GET`/`PATCH`/`DELETE` on a missing-or-non-owned `:id` → typed `not_found` (404),
  opaque `:id` (never coerced → never a framework 422). **POST → 200** (legacy parity), **DELETE → 204**
  (per the task; consistent with the **mindmap** node/edge deletes — note the earlier `tasks` delete returns
  `{success:true}` 200, which this slice intentionally does not follow; legacy returned `{success:true}`).
- **RLS out of scope** (aligns with the Phase-1 slices) — app-layer tenant isolation, tested; RLS later.
  **DB-backed service, no in-memory fallback.** Recurrence, overrides, Google/CRM/source columns, the legacy
  text `project`/`product` columns, calendar-init/bookings/shared-calendars/meeting-requests/CRM, AI
  webhooks, and the React UI are out of scope.

# Tests

- **Create** (DB): all fields → 200, enriched camelCase shape; defaults (`status="planned"`,
  `completed=false`, `tags=[]`, `contactIds=[]`); an explicit `null`/omission for defaulted fields coalesces
  to the default (distinct from PATCH); `completed=true` at creation sets `completedAt`.
- **Priority cascade** (DB): first valid level down `activity → product → project`, else `"medium"`/0.5;
  recomputed from the merged hierarchy on every update; a client `priority` is ignored.
- **Hierarchy fallback (priority only)** (DB): an **activity-only** event derives its priority from the
  activity (and the activity's project/product) via the **event-specific** resolver; its **enriched** read
  reflects the stored ids only (no `projectId`/`productId` → `isOrphan`/`"noProject"`); the task tests still
  pass (no task behavior change).
- **Validation → `validation_error` (422)** (DB): missing/blank `title` (create+update); a non-calendar
  `date` (`2026-02-31`); bad `startTime`/`endTime` (a single-digit hour like `9:05` is **accepted**);
  `endTime <= startTime` (incl. the PATCH effective-value case); a non-array/non-string `tags`/`contactIds`;
  an over-length `color` (>20) / `status` (>20).
- **Time normalization + ordering** (DB): both `startTime` and `endTime` `9:05`→`09:05` on **create and
  PATCH**; same-date `9:05` lists before `10:00`.
- **Enrichment tenant-isolation** (DB): an event whose `projectId`/`productId` points at **another tenant's**
  project does not leak it — enrichment resolves via **owned-project** lookups (`_owned_project`, scoped to
  `sub`), so a non-owned link reads as orphaned (mirrors the task regression `test_tasks_db.py:581`-604).
- **Owned-link → `related_record_not_found` (400)** (DB): create/patch with a missing/non-owned
  `projectId`/`productId`/`activityId`.
- **`SET NULL` on linked-record deletion** (DB): delete a linked **project** → the event's `projectId` is
  auto-nulled (FK `ON DELETE SET NULL`) and the enriched read renders it orphaned (`isOrphan`/`"noProject"`).
- **PATCH** (DB): partial-merge (omitted preserved); `null` on a NOT NULL field → `validation_error`, on a
  nullable field clears it; effective `endTime>startTime`; completion transition (false→true sets, true→false
  clears, omitted leaves); `timezone` sanitized on create **and** PATCH.
- **List** (DB): window filtering (in/out of range); default window when omitted; a **malformed**
  `startDate`/`endDate` → default window (not 422); order `date` then `startTime`; tenant-scoped.
- **Tenant isolation / legacy fix** (DB): a second user's `GET`/`PATCH`/`DELETE` of the first user's event →
  `not_found` (404).
- **Ignored client identity** (DB): a body/query `userId` ≠ `sub` operates on `sub`'s data only; an unknown
  body field is ignored (`extra="ignore"`).
- **Opaque id** (DB): unknown `:id` on `GET`/`PATCH`/`DELETE` → typed `not_found` (404), never a framework
  422.
- **Free-form `status`** (DB): a non-enum value (`"rescheduled"`) round-trips on create + patch (200).
- **Delete** (DB): a successful `DELETE` → 204, then `GET` → 404.
- **Contracts** (`test_contracts.py`): the enriched event camelCase shape + the error envelope (404/422/400).
- **No-PII / typed-error sweep** (review + grep): no raw `HTTPException`; no token/email logged.

|--------------|-------------------|--------------|--------------------|

# Review lenses (pre-answer)

- **Scope / strategy.** Minimum viable: reuses the shipped domain modules, error envelope, and the tasks
  router/service/owned-link/partial-merge patterns; adds one model, one additive migration, one schema
  module, one service, one router, one domain function, and tests. The only net-new domain logic is the
  event priority cascade + the activity-aware resolver (because tasks defers the activity). No new error
  code, no new abstraction. Recurrence, Google/CRM/source, calendar-init/bookings/shared/meeting-requests,
  and the React UI stay deferred (homes named).
- **Architecture.** router→service→async SQLAlchemy (mirrors `tasks.py`); one tenant dependency (`sub`);
  `(sub, id)` lookups; partial-merge via `model_fields_set`; every unhappy path a typed `AppError`. The
  event-specific resolver is isolated in the calendar service; `tasks` is untouched.
- **Completeness.** Activity-aware priority vs stored-id enrichment, the create-vs-PATCH null asymmetry,
  time normalization + ordering, stale-link orphaning, completion transition, list window + malformed-query,
  free-form/over-length status, the legacy GET-by-id security fix — all enumerated + each mapped to a test.
- **Tests & verification.** Each acceptance criterion maps to a named DB test; `make verify` (local Docker
  PG) + `alembic upgrade head` + `alembic check` all green; the migration is applied so tests run on the
  real table.

# Risks & migrations

- **Additive migration (autogenerated, reviewed).** `create_table focal.calendar_events` + indexes; standard
  reversible `downgrade` (drop_table). Risk: autogenerate picking up unrelated drift — mitigated by the
  `focal`-scoped Alembic filter and reviewing the generated file before commit; `alembic check` then guards
  model↔migration drift. No data backfill (new table, empty pre-prod).
- **No task behavior change.** The event-specific resolver is new code in the calendar service; the shipped
  task priority/enrichment is untouched — the existing task tests in `make verify` are the guard.
- **FK `ON DELETE SET NULL` on the links** — matches the shipped `tasks` model + the legacy schema; a
  deleted linked record is auto-nulled and the event then reads as orphaned; tested, not a bug.
- **Shared-DB safety.** Tenancy via the `sub` filter on every query; client `userId` dropped at the schema
  boundary.
