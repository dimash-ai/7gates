# Summary

Implement `focal-calendar-recurrence-read` (slice 1 of 2 for recurring events) on the shipped non-recurring
calendar slice. It adds the recurrence schema, lets `POST /api/events` create a recurring **master**, and
extends `GET /api/events` / `GET /api/events/:id` to **expand** masters into virtual occurrences within the
date window, applying any per-occurrence **overrides** (incl. soft-deletes) and `recurrenceExceptions`. The
recurrence-scoped **mutations** (override writes, "this-and-following" split, group delete) are slice 2
(`focal-calendar-recurrence-write`) and are out of scope. Four independently-green slices: **(1)** schema +
the `recurrence` domain util; **(2)** create-with-recurrence + the read shape; **(3)** expansion in list +
occurrence-id resolution in get; **(4)** contract/migration tests. Task:
[focal-calendar-recurrence-read.md](../tasks/focal-calendar-recurrence-read.md). Binding contract: legacy
`focal/server/{storage,routes}.ts` + `focal/server/utils/recurrence.ts` + `focal/shared/schema.ts`.

## Decisions (design + the Gate-1 rulings)

- **Additive schema, autogenerated migration.** Add six recurrence columns to `CalendarEvent` and a new
  `CalendarEventOverride` model (`focal.calendar_event_overrides`), then `alembic revision --autogenerate`,
  review (focal schema; the `add_column`s; the `create_table` + the unique `(recurring_event_id,
  occurrence_date)` + the `ON DELETE CASCADE` master FK), commit. `calendar_events` is empty pre-prod so the
  NOT NULL `old_logic` add is safe. `alembic check` clean.
- **Recurrence columns** (legacy `schema.ts:302`-308): `recurrence` (String(20), default `"none"`),
  `recurring_event_id` (String, nullable), `recurrence_end_date` (Date, nullable, inclusive bound),
  `recurrence_exceptions` (JSONB `list[str]`, NOT NULL, default `list`), `recurrence_group_id` (String,
  nullable), `old_logic` (Boolean, NOT NULL, default `False`).
- **`CalendarEventOverride`** mirrors the event's **overridable** fields (title/date/start_time/end_time/
  description/location/color/timezone/other_participants; priority/priority_score/priority_level/status/
  completed/completed_at; tags/contact_ids; project_id/product_id/activity_id) + `recurring_event_id`
  (NOT NULL, `ForeignKey("focal.calendar_events.id", ondelete="CASCADE")`, indexed), `occurrence_date`
  (Date, NOT NULL), `is_deleted` (Boolean, NOT NULL, default `False`), `TimestampMixin`, and a **unique
  `(recurring_event_id, occurrence_date)`**. The override's `project_id`/`product_id` →
  `ForeignKey("focal.projects.id", ondelete="SET NULL")` and `activity_id` →
  `ForeignKey("focal.activities.id", ondelete="SET NULL")` — matching the event model (`calendar.py:41`) and
  the legacy override table (`schema.ts:398`). No override **writes** in this slice (slice 2); slice-1 tests
  seed overrides directly via the DB.
- **Recurrence domain util — `app/domain/recurrence.py`** (port `recurrence.ts`): `RECURRENCE_TYPES`,
  `is_recurring_type`; `advance_occurrence(d, recurrence)` (daily +1d, weekly +7d, **monthly +1mo with
  month-end clamp** via `calendar.monthrange`, **yearly +1y with Feb-29→Feb-28 clamp**) — the clamp walks
  from the previous occurrence (iterative, date-fns semantics, so Jan-31 monthly → Jan 31, Feb 28, Mar 28, …);
  `occurrence_dates_in_range(start, recurrence, win_start, win_end, end_date)` (advance to the window, collect
  `≤ win_end`, inclusive `end_date`; **exceptions are NOT skipped here** — the caller does);
  `build_occurrence_event_id(master_id, date)` → `"{id}__occurrence__{YYYY-MM-DD}"`;
  `parse_occurrence_event_id(id)` → `(master_id, date)` or `None` (first `__occurrence__` marker, tolerant).
- **Create** accepts only the rule (`recurrence`/`recurrenceEndDate`/`recurrenceExceptions`); validators:
  `recurrence ∈ {none,daily,weekly,monthly,yearly}` (else `validation_error`), `recurrenceEndDate` a calendar
  date or null, `recurrenceExceptions` an array of `YYYY-MM-DD` (reuse the date validator per element).
  Server sets `recurring_event_id=None`, `recurrence_group_id = id` when `recurrence` is recurring else
  `None`, `old_logic=False` (legacy `storage.ts:3825`-3826). Client `recurringEventId`/`recurrenceGroupId`/
  `oldLogic` are **not** `EventCreate` fields → ignored (`extra="ignore"`).
- **Read shape.** Add to `EventRead` (so the stored row carries them) and thus `EnrichedEventRead`:
  `recurrence`, `recurring_event_id`, `recurrence_end_date`, `recurrence_exceptions`, `recurrence_group_id`,
  `old_logic`. Add to `EnrichedEventRead` only: `occurrence_date` (date|None) and `is_recurring_instance`
  (bool). For a stored row these are `occurrence_date=None`, `is_recurring_instance=False`; for a virtual
  occurrence they are set. camelCase via `by_alias`.
- **List expansion** (port `getAllEventsEnriched`, `storage.ts:3701`-3776): two queries —
  **direct** (`user_id==sub`, `date∈[from,to]`, (`recurrence` null/`none` OR `recurring_event_id` not null))
  and **masters** (`user_id==sub`, `recurring_event_id` null, `recurrence in (daily,weekly,monthly,yearly)`,
  `date ≤ to`, `recurrence_end_date` null or `≥ from`) — then load the overrides map, expand each master via
  `occurrence_dates_in_range` + `_build_occurrence` (skip `is_deleted` overrides and exception dates;
  override-present beats exception), combine, enrich, sort `(date, start_time)`.
- **`_build_occurrence(master, date, override)`** (port `buildRecurringEventInstance`, `storage.ts:3247`-3314):
  `override.is_deleted` → `None`; no override and `date ∈ master.recurrence_exceptions` → `None`; with an
  override → overridable fields from the override, recurrence fields from the master, `id =
  build_occurrence_event_id(master.id, date)`, `recurring_event_id = master.id`; without → master fields with
  `date = occurrence_date`, same synthetic id. Then enrich the resulting object.
- **Get** (`storage.ts:3778`-3819): a **plain id** → the stored row (enriched), tenant-scoped; a **synthetic
  occurrence id** (parse matches) → the owned master must exist + be a recurring master (`recurrence`
  recurring, `recurring_event_id` null) else `not_found`; build the occurrence for the parsed date applying
  the override → `not_found` if excepted/soft-deleted; **no cadence check** (any parseable date builds).
- **Mutation boundary (slice 1).** `PATCH`/`DELETE` operate on the stored row by id as before; a synthetic
  occurrence id → `not_found`. `EventUpdate` does **not** add recurrence fields → `recurrence`/`recurrence*`
  are ignored on PATCH (rule-editing is slice 2). No `recurrenceScope`/`occurrenceDate`, no override writes,
  no split, no group delete.
- Reuse the calendar service's `_enrich`, owned-link, completion, and time-normalization; tenant-scoped to
  `sub`; typed `AppError` only; DB-backed.
- **Enrichable shape (impl note).** A virtual occurrence is **not** an ORM row, so `_enrich` must operate on
  an explicit event-data shape rather than a `CalendarEvent` instance: have `_build_occurrence` return an
  `EventRead` built from the master/override, and adapt `_enrich` to accept either a stored ORM row or a
  built `EventRead` (validate to `EventRead` first, then enrich the resulting dict) so occurrence-only fields
  (`occurrenceDate`, `isRecurringInstance`, the overridden values) never depend on accidental ORM attribute
  access.

   model + `__init__` export; add `app/domain/recurrence.py` with unit-tested helpers; generate + review +

# Tests

- **Create master** (each type) → 200; `recurrenceGroupId == id`, `oldLogic == false`; read carries the
  recurrence fields; client `recurringEventId`/`recurrenceGroupId`/`oldLogic` ignored.
- **Expansion** per type within the window; `recurrenceEndDate` inclusive; `monthly` Jan-31 → Jan-31, Feb-28,
  Mar-28, … (iterative clamp); `yearly` Feb-29 → Feb-28 (non-leap).
- **Exceptions** skipped; an exception date with a (non-deleted) seeded override is **shown** (precedence).
- **Overrides (seeded via DB):** an override changes the occurrence; an `isDeleted` override removes it; the
  occurrence id is `"{master}__occurrence__{date}"`, `occurrenceDate` set, `isRecurringInstance=true`; the
  unique `(recurring_event_id, occurrence_date)` holds.
- **Get by occurrence id** → the single occurrence (override applied); excepted/soft-deleted, or a
  missing/non-owned/non-recurring master → `not_found`; an off-cadence date still builds (not 404).
- **List ordering** (`date`, then `startTime`) across mixed direct + recurring; tenant-scoped; malformed
  list-query date → default window.
- **Validation:** invalid `recurrence`, malformed `recurrenceEndDate`, non-array/non-date
  `recurrenceExceptions` → `validation_error`.
- **Mutation boundary:** `PATCH`/`DELETE` on a synthetic occurrence id → `not_found`; `PATCH` of recurrence
  fields on a master is ignored (rule unchanged) while a non-recurrence field updates.
- **Contracts:** the enriched recurrence fields + `occurrenceDate`/`isRecurringInstance` (camelCase).
- **No-PII / typed-error sweep** (review + grep): no raw `HTTPException`; no token/email logged.

# Review lenses (pre-answer)

- **Scope / strategy.** Minimum viable read path: reuses the calendar service's enrichment/owned-link/
  completion/time-norm; adds one domain util, the recurrence columns + overrides table (additive), create
  support, and expansion. Mutations (override writes, split, group delete) and rule-editing stay in slice 2
  (named). The override table is added now (needed by expansion's override-merge), but written only by slice
  2 / seeded by tests.
- **Architecture.** Pure recurrence logic isolated in `app/domain/recurrence.py` (unit-tested, no I/O); the
  service orchestrates queries + expansion; virtual occurrences are objects, not rows; synthetic ids are the
  occurrence identity.
- **Completeness.** Per-type expansion + iterative clamps + inclusive end + exceptions + override-merge +
  soft-delete + occurrence-id get (no cadence check, matching legacy) + the mutation boundary — each mapped
  to a test.
- **Tests & verification.** `make verify` (local Docker PG) + `alembic upgrade head` + `alembic check`
  green; the recurrence util has standalone unit tests; the migration is pinned.

# Risks & migrations

- **Additive migration (autogenerated, reviewed).** `add_column`s on `calendar_events` + `create_table
  calendar_event_overrides` (+ unique index + CASCADE FK); reversible `downgrade`. `old_logic` is NOT NULL —
  safe because the table is empty pre-prod; no backfill.
- **No mutation behavior change.** Expansion is read-only; the override table is created but only seeded by
  tests this slice. `EventUpdate` is unchanged (recurrence fields not added), so PATCH cannot edit the rule
  yet — intentional, slice 2.
- **Date arithmetic.** The month/year clamps and inclusive end-date are the highest-risk logic; isolated in
  the domain util with direct unit tests (incl. the iterative Jan-31 / Feb-29 cases).
- **Shared-DB safety.** Tenancy via the `sub` filter on the master/direct queries; occurrence enrichment
  resolves only the user's own projects.
