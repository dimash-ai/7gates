# Summary

Restore old-focal Tasks parity in two reviewable sub-slices on the slice-4 worktree
`./superapp-slice4`.

Slice **4a** is frontend-only and shippable: add feature-local task create/edit and info dialogs,
the full old-focal filter/search panel with `localStorage` persistence, inline tag creation,
and schedule-as-event conversion over fields the current FastAPI task contract already supports.
Every mutating path is `canEdit`-gated and every read/write API call threads `currentCalendarId`.
Participant controls are intentionally omitted in 4a rather than squeezing old-focal's multi-party UI
through the current single `contactId`; existing `contactId` values are preserved by not sending that
field unless 4b adds the real multi-participant contract.

Slice **4b** is the backend handoff: add task `recurrence` plus `contactIds[]` and
`otherParticipants` through the SQLAlchemy model, an autogenerated/reviewed Alembic migration,
schemas, service mapping, backend tests, regenerated `openapi.d.ts`, and then wire recurrence and
participant controls into the 4a dialog. The migration is developer-owned and interactive
Claude-Code-under-review per repository rules, not an unattended/manual Codex migration edit.

Assumptions carried from the approved think/task docs: slices 1-3 already landed
`canEdit`/`dataOwnerId`, `calendarId` scoping, and timezone foundation; task `dueDate`/`dueTime` are
wall-clock strings; no drag reorder; no manual priority field; no AI-assistant header button in this
slice.

# Implementation slices

1. **4a.1 - Filter model and storage, no page behavior change.**
   - Add `tasksFilters.ts` with `STORAGE_KEY = "focal-tasks-filters"`, `DEFAULT_FILTERS`, load/save,
     single-id-to-array migrations, allowed date presets, `NO_TAG`, robust localStorage fallbacks, and
     option helpers copied in behavior from old-focal and the current Events filter helpers.
   - Use `getDateRangeFromPreset` and `getRestRangeFromTodayYmd`; do not add `date-fns`.
   - Implement task-specific local date predicates: future presets keep undated tasks and tasks due
     on/after the period start; past/custom presets require a due date inside the range; `all` applies
     no local date predicate.
   - Verify with `tasksFilters.test.ts` before wiring into `TasksPage`.

2. **4a.2 - TaskDialog over current fields only.**
   - Add `TaskDialog.tsx` as a feature-local component using existing shadcn primitives and native
     `input type="date"` / `input type="time"` like the current calendar/event popovers.
   - Fetch the data it needs through existing wrappers: `listProjects(currentCalendarId)`,
     `listActivities(currentCalendarId)`, and `listTags(currentCalendarId)`.
   - Derive root projects and products locally from `listProjects`; reset product/activity when a parent
     selection changes; filter activities by selected product first, then selected project.
   - Save payloads use only current fields: `title`, `description`, `dueDate`, `dueTime`, `tags`,
     `projectId`, `productId`, `activityId`, and `completed` where appropriate. Do not send
     `recurrence`, `contactId`, `contactIds`, or `otherParticipants` in 4a.
   - Inline tag-create calls `createTag({ name, color }, currentCalendarId)`, selects the new tag on
     success, invalidates/refetches tags, and leaves the form open on failure.
   - For existing tasks, show schedule-as-event only when `canEdit` and the task has a due date. The
     action creates an event from task title/description/due date/due time (default start time `09:00`
     only if the due time is empty), project/product/activity, `status: "planned"`, `completed: false`,
     `recurrence: "none"`, and `displayTimezone` from the existing timezone hook. After
     event creation succeeds, delete the source task to match old-focal's task-to-event conversion.
   - Keep all controls disabled while saving/scheduling; never close the dialog on mutation failure.

3. **4a.3 - TaskInfoDialog and page wiring.**
   - Add `TaskInfoDialog.tsx` for read/detail parity: title, due date/time, project-type badge,

     `TaskInfoDialog`, and the header Add button opens `TaskDialog` for create instead of focusing the

   - Keep Active/Completed grouping, old-focal row styling, `compareTasksForDisplay`, orphan badges, and

   - Mutations use existing wrappers and always pass `currentCalendarId`: `createTask`, `updateTask`,
     `deleteTask`, `createEvent`, `createTag`.
   - Every mutation handler starts with `if (!canEdit) return` and the UI disables edit/delete/toggle/
     inline-date/tag-create/schedule actions when `!canEdit`. Reads remain allowed.
   - Invalidate `['tasks']` after task create/update/delete/schedule delete and `['events']` after
     schedule create; do not introduce optimistic/offline behavior in this slice.

4. **4a.4 - Filter/search panel on TasksPage.**

# Review lenses (pre-answer before gate2-plan)

- **Scope / strategy** - The split is the minimum that produces a shippable user-visible win without
  faking fields the backend cannot persist. 4a ports the editor/detail/filter/tag/schedule surfaces over
  current fields; 4b isolates the only schema gap. Existing API wrappers, Events filter patterns,
  `compareTasksForDisplay`, shadcn primitives, and PRIMA `ContactPicker` are reused. No drag reorder,
  no manual priority, no AI header button, no new date picker dependency.
- **Architecture** - 4a keeps task filter logic pure in `tasksFilters.ts` and page behavior in
  `TasksPage.tsx`; dialogs are feature-local components. Data flow is React Query -> derived filter/group
  arrays -> thin mutations. Every write has two gates: UI disabled state and handler-level `canEdit`
  return. `currentCalendarId` is passed through every existing API wrapper that accepts it. 4b follows the
  current backend router -> schema -> service -> SQLAlchemy model pattern and preserves typed errors.
- **Design** - The first screen remains the actual Tasks tool, not a landing page. Old-focal parity
  surfaces are restored with compact operational UI: Active/Completed groups, row affordances, a collapsible
  filter panel, modal create/edit, modal details, and inline tag creation. Loading, empty, filtered-zero,
  read-only, option-error, save-error, and partial schedule-conversion states are named and tested.
- **DevEx** - No shared primitive churn and no handwritten generated types. The plan introduces one pure
  helper module for testable filter behavior, two feature components, focused tests, and one reviewed
  migration in 4b. Future developers can trace each old-focal behavior either to `tasksFilters.ts`,
  `TaskDialog.tsx`, `TaskInfoDialog.tsx`, or the 4b task schema/service fields.

# Risks & migrations

- **4a migration risk: none.** 4a is client-only and uses the existing task/event/tag/project/activity APIs.
- **Schedule conversion partial failure.** Creating an event then deleting the task is a two-step client
  operation. The rescue path is explicit: if create fails, keep the task; if delete fails after create,
  report a partial conversion and keep both records visible rather than hiding either.
- **Participant UI deferred in 4a.** This is deliberate to avoid presenting a multi-participant old-focal
  UI backed by only one `contactId`. Existing `contactId` values are not cleared because 4a omits the field
  from update payloads.
- **4b additive migration.** Add `recurrence`, `contact_ids`, and `other_participants`; keep
  `contact_id` for back-compat. The migration must be autogenerated, reviewed, reversible, and clean
  under `uv run alembic check`. Legacy scalar contact values are surfaced through service/schema fallback,
  not a manual backfill block.
- **Generated API drift.** 4b requires `pnpm gen:api` after the backend is running. If generated output
  changes unrelated schemas, stop and inspect before committing; do not hand-edit generated types.
- **Cross-app contacts.** 4b participant display depends on the existing PRIMA contact read path. If PRIMA
  contact loading fails, the dialog should still allow saving `contactIds` already present by id and should
  show the existing localized contact-picker error for new selections.
- **Rollback plan.** 4a rolls back by reverting client feature files/tests/locales only. 4b rolls back by
  reverting the client wiring plus the additive migration/model/schema/service changes before applying the
  migration to shared environments.
